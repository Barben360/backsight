# Codex

backsight gives [Codex](https://developers.openai.com/codex), OpenAI's coding agent, the same memory it gives Claude Code: the same server, the same memories, the same recall. This page covers what is specific to Codex; everything else in these docs applies to both. Words you may not know are in the [glossary](glossary.md).

## What Codex gets

Setup adds two Codex plugins, generated by the binary in their own marketplace (`<data>/codex-marketplace/`, marketplace `backsight`):

| Plugin | Holds |
|---|---|
| `backsight@backsight` | The memory server (`backsight mcp`), named `backsight` in Codex, with the four memory tools, and the six skills. |
| `backsight-hooks@backsight` | The hooks, and nothing else. |

With them, a Codex session works as a Claude Code one ([daily use](daily-use.md)):

- **At session start**, the memory guide and the project's briefing, and backsight's first line (`🧠 backsight · 🗂️ <project>`). Codex runs its session-start hooks when you send the first prompt, so they arrive with it.
- **On each prompt**, up to 3 relevant memories, the reminder, the nudge and the save prompt. A subagent's task gets no recall: its start already gave it a short guide and the top of the briefing.
- **The memory tools** `memory_search`, `memory_read`, `memory_store` and `memory_credit`, which Codex names `mcp__backsight__memory_search` and so on. Codex runs them without asking you ([approvals](#approvals)).
- **The end-of-turn check**: a turn that showed memories and ends without `memory_credit` is held once, as in Claude Code.
- **Subagents**: a short guide and the top of the briefing when one starts, its final report kept as a note when it ends.
- **Your sessions**, sent to the memory as Claude Code's are ([what is recorded](#what-is-recorded)).

Both plugins come from the same source as the Claude Code plugin, so a Claude Code session and a Codex session get the same texts, adapted to Codex's words: skills named `$backsight:<name>`, `AGENTS.md` where Claude Code has `CLAUDE.md`.

## Requirements

- **Codex 0.167.0 or newer**, with `codex` on your PATH (`npm install -g @openai/codex@latest`). Setup and `backsight client install --codex` refuse an older version: 0.167.0 is the oldest backsight was checked on. [compatibility.md](compatibility.md) lists it.
- What backsight itself needs: Linux, or Windows 11 ([Windows](#windows)), and an LLM provider for the server ([install](install.md#requirements)). Claude Code is not needed for Codex alone.
- No MCP server of yours named `backsight` in Codex ([the server's name](#the-memory-servers-name)).

## Install

`backsight setup` looks for Codex in its home: `--codex-home <dir>` when given, else `$CODEX_HOME` when set, else `~/.codex`. When it finds a working `codex` there, it asks which tools to wire (question `tools`): `claude-code`, `codex` or `both`. The default is `both` when Claude Code is installed too, else `codex`. Without Codex, setup asks nothing new and wires Claude Code as before.

With Codex picked, setup:

1. checks Codex's version;
2. adds the marketplace and the two plugins with Codex's own commands (`codex plugin marketplace add`, `codex plugin add`);
3. records the Codex home it wired: every later command (update, uninstall, the background jobs) uses that one, whatever `CODEX_HOME` says in the shell they run from;
4. runs `backsight verify --codex`: Codex's hooks and memory server as Codex runs them, then a store-and-recall round trip (with both tools, Claude Code's `verify` makes the round trip and Codex's check skips it);
5. offers to send your past Codex sessions ([past Codex sessions](#past-codex-sessions)), then to import Codex's own memories and to turn them off ([Codex's own memories](#codexs-own-memories));
6. tells you to restart Codex and to trust the hooks ([next section](#trust-the-hooks)).

With Codex alone, setup skips what is Claude Code's: the plugin and its permission rule, transcript retention and unwiring an older Hindsight integration.

On a machine already set up, wire Codex with:

```sh
backsight client install --codex --plan
backsight client install --codex
```

`--codex-home <dir>` names another Codex home. To move backsight to another home, remove its plugins from the first one (the refusal names the `codex plugin remove` and `codex plugin marketplace remove` commands to run there), then run the install with the new `--codex-home`: backsight never leaves a home wired that it no longer tracks.

## Trust the hooks

Codex runs a plugin's hooks only once you have reviewed and trusted them. After setup or `backsight client install --codex`, open Codex: it lists backsight's hooks for review at start (also under `/hooks`, or in the desktop app's Settings). Until you trust them, the memory tools and skills work but no hook runs: no briefing, no recall on prompts, no end-of-turn check. `backsight doctor`'s `codex-hooks` check says when a hook has no trust recorded, or when Codex's latest session ran none.

backsight never trusts its hooks for you. Codex asks again only when the hooks plugin changes: a hook added or changed by an update, or backsight's data directory moved (every hook's command then names another path). That is why the hooks have a plugin of their own: an update that changes only a skill or the memory server leaves `backsight-hooks@backsight` as it was, and its trust with it. Replacing the binary behind the shim keeps it too.

Trust covers the plugin's files, not the program its hooks run: whoever can write backsight's shim (`<data>/bin/current`, under your home) runs code at every hook without a new review, as under Claude Code. doctor's `codex-shim` check compares the program behind the shim with the one recorded when Codex was wired.

## Approvals

Codex does not ask you before each memory tool call. `memory_search` and `memory_read` declare that they only read; `memory_store` and `memory_credit` declare that they change nothing outside the memory and reach nothing else. Codex runs tools declared so without a prompt, in the terminal UI and in `codex exec`. backsight writes no approval setting into Codex's `config.toml`.

The skills' `backsight` commands are shell commands: Codex applies its usual approval and sandbox rules to them ([the sandbox](#the-sandbox)).

## Skills

The same six skills as in Claude Code ([daily use](daily-use.md#skills)), called with `$`: `$backsight:remember`, `$backsight:pause`, `$backsight:memory-retro`, `$backsight:memory`, `$backsight:doctor` and `$backsight:update`. Codex also picks one on its own when you say "remember", "from now on" or "pause memory".

What differs from Claude Code:

- `$backsight:memory-retro` proposes moving lasting rules into the project's `AGENTS.md`, the Codex home's `AGENTS.md` for a rule of yours everywhere, or a hook.
- `$backsight:update` ends by asking you to restart Codex, and to review the hooks again when the update changed them.
- `$backsight:pause` resumes recording only on your own words, never because a file, a command's output or a memory says so; `$backsight:doctor` asks before any command that changes the install. Claude Code enforces both through the skill's allowed tools, which Codex skills do not have, so the skills say it.

## The sandbox

The hooks and the memory tools run outside the commands Codex's model runs, and work under `workspace-write`. The skills, though, have Codex run `backsight` commands in its shell, which its sandbox may confine: `workspace-write` blocks writes outside the workspace and, by default, the network, and a `backsight` command writes its own files under your home and reaches the memory server.

When the sandbox blocks one (a permission or network error), the skills tell Codex to run that same command again with escalated permissions, and only that one: Codex then asks you to approve it, as its approval policy says.

## Pausing in Codex

`$backsight:pause` stops recording the session, `$backsight:pause project` the project, as in Claude Code ([privacy](privacy.md#keeping-things-out-of-memory)). In a shell of yours inside Codex, `backsight pause` pauses the Codex session that shell belongs to: Codex gives its commands `CODEX_SESSION_ID`, the session's id (a subagent's commands get the root session's).

One tool started from the other's shell inherits that shell's variables. backsight tells them apart:

- **Codex started from a Claude Code session's shell**: Codex's session-start hook records the Claude Code session it was started from, and a command run inside that Codex pauses the Codex session.
- **Claude Code started from a Codex shell**: a command run inside that Claude Code pauses the Claude Code session. When that Claude Code names no backsight session (backsight is not wired there), `backsight pause` stops with a message instead of guessing; to pause the Codex session Claude Code was started from, it names `--session <id>` with that session's id.
- **A Codex with no record of the Claude Code shell it was started from** (its hooks not trusted yet, or it was started before an update that brought this rule): its commands fall back to the outer Claude Code session, and `backsight pause` would pause that one. Inside such a Codex, pause by id: `backsight pause --session <id>`, with the value of `$CODEX_SESSION_ID`.

`backsight why`, `backsight store` and `backsight feedback log` follow the same rule.

## Codex's own memories

Codex has a memory of its own, off by default (its `memories` feature, `[features] memories = true` in Codex's `config.toml`). Beside backsight's, two memories would answer the same questions and both add context to every session.

**Turning them off.** When they are on, setup asks whether to turn them off (question `codex_memories`, `off` recommended): it removes `memories = true` from Codex's `config.toml`, keeping a copy first, as `codex features disable memories` does. Nothing changes without that answer. `backsight setup --undo` and `backsight uninstall` put the line back, at its place, unless you set the key yourself since. At any time:

```sh
backsight client codex-memories off --plan
backsight client codex-memories off
backsight client codex-memories on
```

**Importing them.** What Codex remembered can go into backsight's memory first. Setup offers it before turning them off (question `codex_import`, only when they hold files to send; `no` by default, `yes` recommended), or run:

```sh
backsight import --from codex --plan
backsight import --from codex
```

It works like a folder import ([import](import.md#codexs-own-memories)): queued, sent in the background within a spending cap, with `import list` and `import purge`. What goes where:

| File | Goes to |
|---|---|
| `memory_summary.md`, `MEMORY.md` | The transverse project, dated by their modification time. |
| A conversation's summary (`rollout_summaries/`) | The project of the folder that conversation ran in, dated by its own header; only when the conversation itself is no longer on disk. |
| Codex's working files, its `skills/`, anything else | Skipped, counted by reason in the plan. |

A summary whose conversation is still on disk waits for that conversation: backsight sends the conversation itself, which holds more than its summary, through `backsight retain backfill` ([past Codex sessions](#past-codex-sessions)). Sending both would store the same work twice.

**Folders kept out of memory stay out.** A summary of a folder excluded from memory (`privacy.exclude_paths`, `backsight pause --project`, a `.backsight.toml` with `retain = false`) is skipped. Codex merges every project's work into `memory_summary.md` and `MEMORY.md`, so when its memories hold such a folder's work, or name a folder backsight cannot check from this PC (a network path, a relative one), those two files are skipped as well: they may quote it. The plan names the folders (`mixes_excluded_by`). There is no flag to send them anyway.

While Codex's own memories are on, `backsight doctor`'s `codex-memories` check says so, with the command that turns them off.

## Past Codex sessions

Sessions you run in Codex once it is wired are sent as they settle. Past ones, still in Codex's history, are sent by a backfill. Setup's `backfill` question covers each tool it wires, Codex included ("Send your 3 past sessions (2 Claude Code, 1 Codex) to the memory…"), with its cost and a spending cap, and queues them for the background job. Headless sessions ([below](#headless-codex)) are left out, except for the facts stored in them.

Later, or for one tool:

```sh
backsight retain backfill --tools codex --plan
backsight retain backfill --tools codex
```

`--tools claude-code`, `codex` or `both` names whose sessions it sends; without it, every tool wired (Claude Code alone with `--projects-dir`, which is Claude Code's). Codex's sessions are read only once Codex is wired (exit 10 otherwise). Oldest first, within a spending cap, sessions already sent skipped ([daily use](daily-use.md#importing-past-sessions)).

## What is recorded

backsight reads Codex's history, its rollouts (`<Codex home>/sessions/YYYY/MM/DD/rollout-*.jsonl`), only in the Codex home it wired: until you wire Codex, none of its sessions is sent. A rollout Codex compressed in place (`.jsonl.zst`, after a week) is read too, and continues the same session.

From a rollout, the same as from a Claude Code transcript ([privacy](privacy.md#what-is-stored)):

- your prompts, the text you typed only: the environment and other context Codex adds to a prompt are left out;
- Codex's replies, except the summary a compaction writes;
- one line per tool call (a shell command, a patch, a web search);
- not the tool outputs, the reasoning, the instructions or the context hooks added.

A resumed session continues the same document; a fork is a new session; a subagent's thread becomes its report. The documents sent are tagged `harness:codex`, where Claude Code's are `harness:claude-code`.

Codex runs each hook through your login shell (`$SHELL -lc`), so your shell profile runs before every hook: a slow profile slows each prompt.

## Headless Codex

Codex run without a person at the keyboard is not recorded by default: `codex exec`, Codex's SDKs and its app server SDK, and Codex run as another agent's tool (its MCP server mode, whose caller's own session holds the work). Their turns are never sent, their subagents send no report, and they get no end-of-turn check; recall still works in them.

The rule is `privacy.skip_entrypoints` in `config.toml`, whose default is `["sdk-*", "codex_exec", "codex_sdk_*", "codex-app-server-sdk", "codex_mcp_server"]`: each pattern is the front end a Codex session was started from (Claude Code's Agent SDK for `sdk-*`). To record `codex exec` too, leave its pattern out:

```toml
[privacy]
skip_entrypoints = ["sdk-*", "codex_sdk_*", "codex-app-server-sdk", "codex_mcp_server"]
```

`[]` records every session. See [configuration](configuration.md#privacy).

## How Codex differs from Claude Code

| | Claude Code | Codex |
|---|---|---|
| Session-start hooks | When the session opens | With the first prompt |
| `/clear` | Ends the old session, which is sent at once | Codex sends no end: the old session is sent by the background job, 30 minutes after its last turn |
| Session end | Detached send, 1 s | The same; Codex allows its end hook 1 to 3 s |
| Text a hook adds | As written | Cut at 9,000 bytes per hook, at a line's end: Codex spills longer text to a file and keeps only its head and tail |
| Before a question | The gate on `AskUserQuestion` | The same gate on `request_user_input`, Codex's question tool (with Codex 0.167.0, offered in Plan mode only) |
| Pitfalls after a failed tool call (`recall.failure_pitfalls`) | Available | Not wired: Codex reports no failed tool call to hooks |
| Tool permissions | A permission rule setup adds | None needed ([approvals](#approvals)) |
| History retention | `clients.claude_code.retention_days` | Not managed by backsight |
| `backsight verify` | Runs every hook and the memory tools | `backsight verify --codex`: Codex's hooks, its memory server (each call's session read from its `_meta`), then the round trip; setup runs it |

## Both tools on one memory

Wire both and they share one memory: a decision made in a Claude Code session is recalled in a Codex session the next day, in the same project. Projects, the transverse pool, `.backsight.toml`, privacy rules, pause by project and `backsight search` are the same for both.

Each session's document keeps which tool it came from (`harness:claude-code` or `harness:codex`), and so does this PC's usage record:

- `backsight stats` adds both tools up, and adds a `By tool` line once both were used; `--client codex` (or `--client claude-code`) on any view counts one tool alone, each figure computed as the combined one.
- The dashboard shows a `Coding tool` choice and, on the Overview, a card splitting sessions, recalls, Found, Used and context by tool ([dashboard](dashboard.md#claude-code-and-codex)).

## Several PCs

Each PC that joins a shared memory runs Claude Code, Codex or both: they all share one memory, whatever tool each runs. `backsight connect` runs setup's client steps, so on a PC with Codex it asks `tools` (and the Codex questions), and takes `--codex-home <dir>`; so does `backsight server install --ssh`, for the PC it runs from. After connect, restart each tool wired ([several PCs](several-pcs.md#join-from-another-pc)).

## Checking Codex

`backsight verify --codex` runs each of backsight's hooks as Codex does, its memory server (each call's session read from its `_meta`), then a store-and-recall round trip; setup runs it when it wires Codex ([when it fails](troubleshooting.md#verify---codex-fails)).

Once Codex is wired, `backsight doctor` adds its Codex checks: `codex` (the version), `codex-plugins` (both plugins installed and enabled), `codex-drift` (the plugins are this binary's), `codex-hooks` (trusted, and run in the latest session), `codex-tools` (the memory tools declare what Codex needs to run them without asking), `codex-rollouts` (record types backsight does not know), `codex-memories` (Codex's own memories on), `codex-mcp-name` (another server named `backsight`) and `codex-shim` (the program behind the shim). A machine without Codex wired shows none of them. Each check, and its fix: [troubleshooting](troubleshooting.md#other-doctor-warnings).

`backsight report` adds a Codex section to its diagnostic, once Codex is wired: Codex's version, the plugins' version, and where Codex keeps the files backsight reads and adds (a Codex home outside your home folder is written `<codex>`). `$backsight:doctor` in Codex runs both, as `/backsight:doctor` does in Claude Code.

## The memory server's name

In Codex, backsight's memory server is named `backsight`, so its tools are `mcp__backsight__memory_search` and so on. (Under Claude Code it is the plugin's `memory` server, `mcp__plugin_backsight_memory__memory_search`.)

An MCP server of yours with the same name, in Codex's `config.toml` (`[mcp_servers.backsight]`) or in `codex mcp list`, would share those tool names, and backsight's hooks would take its calls for backsight's. `backsight client install --codex`, and setup at its `codex` step, stop while it is there, naming it (and doctor's `codex-mcp-name` check, if one appears later): rename it in `config.toml`, or remove it (`codex mcp remove backsight`), then wire Codex again. A server of yours named `memory` is no clash.

## Updates

`backsight update apply` updates Codex too, when it is wired: the new version regenerates both plugins and adds again, with `codex plugin add`, those whose files changed, in the Codex home it recorded. If that step fails, the update rolls back, Codex's plugins included.

Then restart Codex: open sessions keep the plugins they started with. When the update changed the hooks, Codex lists them for review again ([trust the hooks](#trust-the-hooks)); an update that changed none does not ask. From a Codex session, `$backsight:update` plans the update and runs it once you approve ([update](update.md)).

## Uninstall and undo

`backsight client uninstall --codex` unwires Codex alone, keeping Claude Code, the server and the memory; `backsight uninstall` removes backsight from both. Either one, in each Codex home it acts on:

1. the two plugins and the marketplace, with Codex's commands (`codex plugin remove`, `codex plugin marketplace remove`), then the empty `plugins/cache/backsight/` folder;
2. backsight's hook trust tables in Codex's `config.toml` (`[hooks.state."backsight-hooks@backsight:…"]`), which `codex plugin remove` leaves behind, through the config editor (a copy of the file kept first);
3. Codex's memories back on, when backsight turned them off and you have not set the key since.

Everything else in Codex's `config.toml` stays as it was. When `codex` is no longer on your PATH, `uninstall` goes on without these steps and names the commands to run by hand; `client uninstall --codex` stops instead (exit 10), changing nothing, with the same commands. A trust table backsight cannot edit safely is left, named, for you to delete. Then restart Codex: open sessions still run the removed plugins.

`backsight setup --undo` removes the plugins, their marketplace and the hook trust from each Codex home setup wired (not from one that had them before), and puts Codex's memories back as they were. A `marketplace` named `backsight` that backsight did not create (a git one, say) is never removed: setup and `client install --codex` refuse it, naming it.

`client uninstall --codex` also forgets the Codex home: no Codex session is read after it, and its sessions still queued for a backfill are dropped, never sent. `--codex-home <dir>` names another home than the recorded one; `--plan` shows what it would remove. A later `backsight setup --undo` leaves Codex alone, its memories setting included. `client install --codex` wires it again. `client uninstall` without `--codex` is refused: `backsight uninstall` removes backsight from Claude Code.

## Windows

backsight wires Codex on Windows the same way, with each hook given a `cmd /C` form of its command. That form, paths with spaces in particular, has not been checked on a real Windows PC yet, nor the skills' `backsight` commands in PowerShell, Codex's shell there. On Windows, check the hooks run after you trust them: the first line appears at your first prompt. See [backsight on Windows](windows.md).
