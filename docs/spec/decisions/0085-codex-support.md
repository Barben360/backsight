## Context

The study behind the epic read Codex's docs and source (openai/codex `0d37c06`, 0.167.0). Block 1 ran a real Codex 0.167.0 in a container against backsight's development build, a fake model and a scratch server, and recorded what Codex does (C14; fixtures in backsight `internal/testdata/codex/0.167.0/`). Most of the study holds; these facts change the design:

- A Codex hook handler is **one shell command string**: the exec form's `args` is ignored, so today's generated hooks would run the shim with no arguments.
- The memory tools are **`mcp__memory__<tool>`** for Codex (a namespace tool `mcp__memory` for the model), not the plugin-prefixed Claude names.
- Plugin hook trust pins **every file of the plugin folder**: any change to a skill, the manifest or `.mcp.json` asks the user to review all the plugin's hooks again.
- `codex exec` denies a tool without hints, but runs one that declares `destructiveHint: false` and `openWorldHint: false`, in the TUI too, **without any config edit**.
- One MCP server process **per thread** by default (each subagent gets its own); sharing one process across chats exists only behind two development flags.
- Shell commands get `CODEX_SESSION_ID` (the root session); hooks get Codex's whole environment; the MCP server gets almost nothing.
- Hook `additionalContext` over 2,500 tokens is **spilled** (head and tail kept, the rest saved to a file), not cut.

## Decision

### D1 — The client layer (block 2)
- One adapter per client, Claude Code first (no behaviour change), Codex second. A Codex adapter answers:
  - home: `$CODEX_HOME` when set and non-empty, else `~/.codex`, resolved once at setup and **recorded per client** (never re-read from the shell later, the `CLAUDE_CONFIG_DIR` lesson); `--codex-home` overrides;
  - detection: `codex --version` (`codex-cli <x.y.z>`) at least the minimum (D9);
  - tool-name prefix `mcp__memory__`; harness tag `harness:codex`;
  - hook input: Claude's fields plus `turn_id` (every turn-scoped event), `model`, `permission_mode`, and `agent_id`/`agent_type` on every event of a subagent; `tool_response` is an object for MCP tools, a string for `Bash` and Codex's own tools;
  - hook output: the same JSON as Claude (`hookSpecificOutput.additionalContext`, `systemMessage`, Stop `decision: "block"`), all accepted unchanged on 0.167;
  - conversation store: rollouts (D7);
  - texts: `AGENTS.md` for retro targets, `$backsight:…` / implicit skills, the `/hooks` review.

### D2 — The Codex plugins (block 3)
- Generated from the same source as the Claude plugin, in a **separate marketplace folder** (`<data>/codex-marketplace/`, marketplace `backsight`), so a Claude update never touches the Codex tree. The manifests stay `.claude-plugin/plugin.json` and `.claude-plugin/marketplace.json`: Codex reads them; no `.codex-plugin/` is needed.
- **Two plugins** (hook trust, D5):
  - `backsight@backsight`: `.mcp.json` (exec form, the shim, `["mcp"]`, `env_vars = ["BACKSIGHT_HOME"]` so a non-default home reaches the server) and `skills/`;
  - `backsight-hooks@backsight`: the manifest and `hooks/hooks.json` only. Its manifest `version` is a hash of the hook set, not the binary version, so its bytes change only when a hook changes.
- Each handler: `"command": "<shim> hook <event>"` with the shim path quoted for `sh`, `"commandWindows"` quoted for `cmd /C`, an explicit `timeout` on every handler (Codex defaults to 600 s), no `args` (C14 §1: the exec form's `args` is ignored, recorded). `commandWindows` and its `cmd /C "<command>"` run come from the source only: **unverified on Windows**, block 3 checks the quoting there (paths with spaces).
- Install: `codex plugin marketplace add <dir>` then `codex plugin add backsight@backsight` and `codex plugin add backsight-hooks@backsight`; checked with `codex plugin list --json` (`installed`, `enabled`, `source.path`). Update: regenerate, then `codex plugin add` again for each plugin whose files changed (Codex re-copies a local plugin only then, same version or not).

### D3 — Behaviour per Codex hook (block 4)

| Codex event (matcher) | Timeout | backsight |
|---|---|---|
| SessionStart `startup` | 10 s | As Claude: guide, briefing, first-session notice, banner. Fires at the first prompt. |
| SessionStart `resume\|clear\|compact\|fork` | 5 s | As Claude. `fork` is a new session (new id, new document). `compact` arrives at the turn after a compaction: the re-briefing of 0083 C5 happens there. `/clear` ends the old session **without SessionEnd**: it settles by the idle rule (§9.1). |
| UserPromptSubmit | 25 s | As Claude. **With `agent_id` set it is a subagent's task**: no prompt recall, no reminder (SubagentStart already gave the short guide). Stop-block continuations do not fire it. |
| PostToolUse `mcp__memory__.*` | 2 s | As Claude, journaling with `session_id`, `turn_id`, `agent_id` and `tool_use_id` (= `_meta.callId`); `tool_response.content[].text` is the result. A failed or denied call fires nothing. The matcher also matches a user's own MCP server named `memory` (C14 §2): setup and doctor read `codex mcp list --json` and `config.toml`'s `[mcp_servers.memory]`, and refuse (setup) or warn (doctor) on such a server, naming it. |
| PreToolUse `request_user_input` | 10 s | The question gate of SPEC §6.2, mapped to Codex's question tool. Measured: the tool is offered and its PreToolUse fires in Default mode, where the tool then refuses itself ("unavailable in Default mode"); from the source it works in Plan mode only (C14 §8). The gate is wired anyway; whether it ever matters in Plan mode is **to confirm with a real model**. |
| Stop / SubagentStop | 5 s | As Claude: the end-of-turn credit check answers `decision: "block"` and honours `stop_hook_active`; subagent reports from `agent_transcript_path`. |
| SubagentStart | 5 s | As Claude: short guide and briefing items (a developer message before the task). |
| SessionEnd | 1 s (Codex clamps to 1-3 s) | As Claude: detached `retain flush`. `reason` is always `other`. Root threads only. |
| PreCompact, PostCompact, PermissionRequest, Interrupt, PreModelRequest, PostModelRequest | — | Not wired. |

- **Failure pitfalls** (PostToolUseFailure, 0083 C9): no Codex equivalent (an MCP call that fails or is denied fires no PostToolUse at all): not wired for Codex.
- **Budgets**: every injected text stays under 9,000 bytes per handler (Codex counts bytes / 4 against its 2,500-token spill threshold); `additionalContextLimit` is not raised (a spilled briefing keeps only its head and tail).
- **Supervisor**: unchanged; it always ends without blocking Codex. Exit 2 blocks in Codex as in Claude.
- Codex runs each hook through `$SHELL -lc` (a login shell): the user's profile runs before every hook. Block 10 measures the cost on the author's machine.

### D4 — Identity (block 5)
- The MCP server reads the session **per call** from `_meta`: `sessionId` (the root session, equal to the hooks' `session_id`), `x-codex-turn-metadata.turn_id`, and `callId` (equal to the hooks' `tool_use_id`). Inside a subagent `sessionId` is still the root; `threadId` is the subagent's and is not the session. Verified equal to the hooks' `session_id` in a fresh session, a subagent, after `/clear`, after `codex exec resume` and in a fork (C14 §6-§7, `checks/5-identity/pairs.json`).
- No per-process session state for Codex: by default each thread starts its own server process, and under Codex's sharing flags one process serves several threads (verified); both must work.
- A Codex call without `_meta.sessionId` fails closed where the session matters, as the Claude path does without its record.
- **Amends SPEC §7** for Codex: where §7 takes the session from the by-pid record, the Codex server takes it from that call's `_meta.sessionId`: the `recall` journal line it writes after each `memory_search`, `memory_credit`'s check of its ids against the session's journal shows, short ids in `memory_read`, pause, and `memory_store`'s privacy checks. The shows and credits themselves stay journaled by the PostToolUse hook (D3), as for Claude.
- `backsight pause` from a Codex shell reads `CODEX_SESSION_ID` (the root session), not `CODEX_THREAD_ID`.

### D5 — Hook trust (block 3)
- backsight never writes `trusted_hash` or `trusted_content_hash`. Setup tells the user to open Codex and trust the hooks in the review it shows (or `/hooks`, or the app's Settings), once after install and again when an update changed `backsight-hooks`.
- What re-asks: a change to a hook's event, matcher, command, timeout, status message or context limit, or **any byte of the hooks plugin's folder** (Codex hashes the whole folder). Recorded (C14 §3, `checks/`): in one plugin, a changed skill or a bumped version stops all its hooks until reviewed; with the split of D2, a changed skill in `backsight@backsight` leaves `backsight-hooks` trusted and running, and only a change to `backsight-hooks` itself re-asks; replacing the binary behind the fixed shim keeps the trust. A moved data directory changes every command and re-asks.
- **Rejected: the hooks in the user's `$CODEX_HOME/hooks.json`.** A user-level hook is trusted on its declaration alone (no content hash, C14 §3), so it would re-ask exactly when D2's hooks plugin does; but it means editing a file the user owns and shares with their own hooks (a JSON editor beside D8's TOML one, its undo and drift), it falls outside `codex plugin list` and `codex plugin remove`, and plugin hooks get `PLUGIN_ROOT`/`PLUGIN_DATA` that user hooks do not. The hooks plugin gives the same trust behaviour with Codex's own install commands.
- **Security**: trust covers the declaration and the plugin folder, not the program behind the shim path. Whoever can write `<data>/bin/current` (or what it points to) runs code at every hook with no new review: the same exposure as under Claude Code, where the plugin also runs the shim. The shim lives in the user's own data directory (mode 0755 under their home); doctor already checks the shim target against the installed binary (SPEC §5 drift), and for Codex also reports a shim target whose sha256 differs from the one recorded at install.
- Doctor reports untrusted hooks from `[hooks.state."backsight-hooks@backsight:hooks/hooks.json:<event>:<g>:<h>"]` (a `trusted_hash` per wired handler) and from a heartbeat: SessionStart records each run per client, and a Codex rollout newer than the last recorded run means the hooks did not run.

### D6 — Tool approvals (blocks 3 and 5)
- `memory_store` and `memory_credit` declare `destructiveHint: false` and `openWorldHint: false` (`memory_search` and `memory_read` keep `readOnlyHint: true`). No `config.toml` key is written for approvals.
- Measured on backsight's own server with those hints added by the harness (C14 §4, `checks/4-approvals-with-hints/`): `memory_store` and `memory_credit` ran with no prompt in the TUI (policy `on-request`) and in `codex exec` with `workspace-write` (policy `never`). From the source: `untrusted` and `granular` prompt only when an approval is needed, as `on-request` does, so the hints spare the prompt there too; only `never` turns a needed approval into a denial.
- Claude Code: SPEC §5 records that `readOnlyHint` does not skip its prompts (E15); `destructiveHint` and `openWorldHint` are **untested on Claude Code**. Its permission rule stays whatever they do, so adding them cannot add a prompt there; block 5 checks a Claude session once.
- Fallback, if a later Codex stops honouring the hints: `[plugins."backsight@backsight".mcp_servers.memory.tools.<tool>] approval_mode = "approve"`, the key Codex's own "Always allow" writes, through D8's editor.

### D7 — Conversations (block 6)
- Discovery: `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-*-<thread id>.jsonl`, and `.jsonl.zst` (zstd) for a rollout compressed in place (`features.local_thread_store_compression`, after 7 days). The JSONL is authoritative; the SQLite projection of paginated history (`thread_history_1.sqlite`) is not read.
- A thread's document is keyed on its id; resume appends to the same file and continues the document; a fork is a new thread and a new document; a thread whose `session_meta` has `parent_thread_id` (`source.subagent.thread_spawn`) is a subagent report.
- Unknown record types are counted for doctor. Seen on 0.167: `session_meta`, `turn_context`, `response_item`, `event_msg`, `compacted`, `world_state`, `token_usage_record`.
- Attribution: `exec_command` (`cmd`) and `apply_patch` in its arguments; with a model Codex has no metadata for, edits arrive as `apply_patch` heredocs inside `exec_command`.

### D8 — The TOML editor (block 3)
- Narrow: it changes whole tables or single keys of `config.toml` under the config editor's rules (pre-image, journal, write only if the file did not change meanwhile, undo), never Codex's other files. Its uses:
  - uninstall and undo remove backsight's own `[hooks.state."backsight@backsight:…"]` and `[hooks.state."backsight-hooks@backsight:…"]` tables, which `codex plugin remove` leaves behind (verified);
  - turning Codex's own memories off (D10), when the user consents;
  - the approval fallback of D6, only if needed.
- Plugins and marketplaces are added and removed with Codex's own commands, never by editing the file.
- Uninstall also removes the empty `plugins/cache/backsight/` folder; Codex's `.hook-trust/` baseline file is Codex's, left alone.

### D9 — Minimum Codex version
**0.167.0**: every fact above was observed on it; no older release was run, so none is claimed. Setup and doctor refuse an older `codex`.

### D10 — Codex's own memories
- A stable feature, off by default: `[features] memories = true` turns it on (or a profile, or `--enable memories`).
- Doctor reads `codex features list` (the effective state, row `memories`) and warns when it is on, recommending to turn it off, for efficiency (two memories would answer the same questions).
- Setup offers to turn it off, only with the user's consent, recommending it. Off means removing `memories = true` (what `codex features disable memories` does), through D8's editor so undo restores it.
- **Importing them (#287 https://github.com/Barben360/backsight/issues/287) goes ahead**, with the layout the spike found (C14 §11), which differs from the study's:
  - the store is `memories_v2/` (a fresh profile) or `memories/` (v1, an older one), or both under dual write; import every store present;
  - send `memory_summary.md` (both versions) and `MEMORY.md` (v1 only; v2 has none), to the transverse project, dated by their modification time (0081's rule);
  - send a `rollout_summaries/*.md` file only when its `rollout_path:` no longer exists (backfill sends the rollouts that do); its header gives the thread id, the date (`updated_at`) and the working folder (`cwd`), so it goes to **the project of `cwd`** (the same resolution as a session's) **with its `updated_at`**;
  - send the notes of `extensions/*/resources/*.md`, dated by their name; this path comes from the source only, **never observed** in the runs (Codex wrote no note), so the reader skips it with a reason until a real store shows one;
  - skip `raw_memories.md` (v1: a merge Codex rebuilds from its database), `extensions/*/instructions.md`, `phase2_workspace_diff.md`, `skills/`, `.git/` and `.codex-baseline/`;
  - the content of the consolidated files is the model's: their real sizes and quality are for block 10's live check. The format is generated state with no guarantee: the import keeps to files and headers, and a file it cannot read is skipped with its reason.
- **Amends 0081: a source may map each file to a project and a date.** Chosen over "everything transverse, the date in the text": a summary of work in `~/src/foo` belongs to `foo`'s recall, and 0081's anti-goal is exactly content dated wrongly. It needs no new machinery beyond the per-file mapping:
  - the reader (the `--from codex` preset) returns, per file, a project and a date (`cwd` resolved as for sessions, `updated_at`); the generic `import <path>` keeps 0081's rules (one project, frontmatter or mtime);
  - the manifest's file entries gain `project` (the source's `project` stays the default); the document id (`import:<source>/<path>`) does not change, so re-import, `import list` and `import purge <source>` work as in 0081;
  - `--plan` and the cap count per project as well as per folder; a re-import whose mapping changed a file's project sends it again with the same document id (its tags follow).

## Tests that must bite
Each replays the recorded fixtures (backsight `internal/testdata/codex/0.167.0/`) and fails when the behaviour is missing:
- **Generator** (block 3): the Codex `hooks.json` has no `args` and every `command` ends with `hook <event>`; the PostToolUse matcher matches `mcp__memory__memory_search` and not `mcp__plugin_backsight_memory__memory_search`; every handler has a `timeout`; `backsight-hooks`' folder is byte-identical across two generations that differ only in binary version or skill text, and differs when a hook changes.
- **Hook input** (blocks 2, 4): each `hooks/*.json` fixture decodes; `tool_response` as object (MCP) and as string (`Bash`); a `UserPromptSubmit.subagent.json` (with `agent_id`) gets no recall; Stop answers `decision: "block"` once and nothing with `stop_hook_active: true`.
- **Identity** (block 5): a `tools/call` from `mcp/root.in.jsonl` and one from `mcp/subagent.in.jsonl` resolve to the same session; two sessions' calls on one server process never see each other's shows; a call without `_meta.sessionId` is refused where the session matters.
- **Approvals** (block 5): the served `tools/list` carries `destructiveHint: false` and `openWorldHint: false` on `memory_store` and `memory_credit`, `readOnlyHint: true` on the two others.
- **Rollouts** (block 6): `rollouts/root.jsonl` and `compressed.jsonl.zst` give the same segments; `fork.jsonl` is a new document, `subagent.jsonl` a subagent report; an unknown record type is counted, never fatal.
- **TOML editor** (block 3): uninstall on `checks/6-removal/config-after.toml` removes exactly backsight's `[hooks.state]` tables, byte for byte otherwise; undo restores them.
- **Import** (block 11): the `memories/<v2|v1|dual>` fixtures give the plan of D10: files sent with their project and date, files skipped with their reason, a summary skipped while its `rollout_path` exists.

- **D1, the client layer**: `internal/harness` (an `Adapter` of small interfaces; a registry with Claude Code first and the default) and the ids in `internal/harnessid` (`claude-code`, `codex`). Every telemetry event and journal line carries `client` (index migration `0006-client`; a line without it reads `claude-code`). `HookInput` gained `TurnID`, `ToolUseID`, `Model`, `PermissionMode` (Claude Code's decoder leaves them zero); `HookOutput` is unchanged: Codex reads Claude Code's answer JSON.
- **Per-tool config and state**: `[client]` became `[clients.claude_code]` (`retention_days`), and `[clients.codex]` parses with no key; client migration `0100-clients-table` renames the header in place through the config editor (`client config restore` undoes it); the old name is still read, both names with different values are refused. **An older binary refuses `[clients.claude_code]`**: the release notes and troubleshooting say to rename it back to `[client]` before installing an older release by hand (the coordinator's ruling: the cost is a manual downgrader's hooks failing until they read it). `state.json` keeps Claude Code's entry under `client` (older binaries read it) and the others under `clients`.
- **The Codex MCP server is named `backsight`** (author, 2026-11-11: "Perfect for backsight for the Codex MCP server."): Codex names a plugin's tools `mcp__<server>__<tool>` without the plugin, so `memory` would clash with any server of the user's called `memory`. Tools `mcp__backsight__memory_search|memory_read|memory_store|memory_credit`, PostToolUse matcher `mcp__backsight__.*`, approval fallback key `[plugins."backsight@backsight".mcp_servers.backsight.tools.<tool>]`: this replaces `mcp__memory__` in D1, D3 and the tests, and D6's key. The clash check (setup and `client install --codex` refuse, doctor warns) is on a user server named `backsight` (`[mcp_servers.backsight]`, `codex mcp list`); one named `memory` is no clash. Claude Code keeps `memory` (its names carry the plugin); `serverInfo.name` stays `memory` for both. The fixtures were rewritten by `scripts/codex/rename-server-fixtures.sh`; a live check on 0.167.0 is recorded in `server-name/`.
- **Command lines (D2)**: hook handler `"<shim>" hook --harness codex <event>` (the shim sh-quoted in `command`, cmd-quoted in `commandWindows`, where a path holding `"`, `%` or a control character is refused); the generator test reads "every command ends with `hook --harness codex <event>`", not `hook <event>`. Memory server: the shim with `["mcp","--harness","codex"]`, `env_vars ["BACKSIGHT_HOME"]`. `--harness` is a hidden flag of `hook` and `mcp`, default `claude-code`: Claude Code's plugin and its version hash are unchanged.
- **D2, D8, D9, install**: as decided (`<data>/codex-marketplace/`, the hooks plugin's version a hash of its `hooks.json`, minimum 0.167.0). `client install --codex [--codex-home D]` records the home, the plugin version, the shim's sha256 and the wiring time; `client codex-memories off|on [--plan]`; `update apply` runs the new binary's `client install --codex` when Codex is wired (the previous binary's on a rollback). **D8**: the adapter's `Uninstall` runs Codex's own commands only; the `[hooks.state]` tables are removed by the CLI through the config editor (it holds the journal and pre-images), with the same result. - **D3, hooks**: as the table, and: every injected text cut to 9,000 bytes at its last whole line; prompts Codex writes itself (its contextual user fragments: `AGENTS.md`, `<environment_context>`, `<user_shell_command>`, …) skipped as machine messages; a subagent's UserPromptSubmit (Codex only) begins no turn (telemetry `prompt` with `reason: subagent`).
