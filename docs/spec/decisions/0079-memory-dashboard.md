# 0079 — Memory dashboard: how well memory works, in a browser and as JSON

- **Date**: 2026-10-30
- **Status**: accepted, revised after two rounds of independent reviews (see "Review log"), before any plan
- **Decided by**: author (2026-10-30: "a dashboard served by `backsight dashboard` … rich information about our memory system health, not only the services health, but the efficiency of the memory system itself"; "any data we see on the dashboard should also be queryable through backsight CLI, for agents to access them too"; SQLite approved, "don't forget about the migration system when updating"; audience "any user + developer"; "I follow whatever you think is best for the user and developer, and the technical details"), on the agent's proposal. Every choice not quoted here is the agent's, open to veto; the notable ones are tagged *(agent's call)*. One change to what the author approved in chat: the feedback journal stays an append-only JSONL file for good, and only the ledger moves to SQLite (§12 says why).

## Intent

backsight already measures a great deal about how memory behaves: every recall, every memory shown and at which rank, every declaration Claude makes about what it used, every retirement, every send, every hook failure (telemetry, A.4; feedback journal and ledger, 0074). Only `stats` reads most of it, as one dense block of totals with no trend, no drill-down and no per-memory view, and several recorded fields are read by nothing (rank of the used memory, reranker scores, `memory_search` latency and hits, retain duration, `doctor-snapshot.json`) or shown by no view (the combined shared ledger, which only recall reads). The server holds more (growth over time, counts per project, consolidation backlog, extraction tokens per operation) that backsight never asks for.

This decision gives every user, and the developer, one place to answer "is my memory working, is it right, is it worth what it costs, and what should I do about it", in a local browser page served by `backsight dashboard`, with **every number also available from the CLI as JSON** for agents.

### Goals
- **G1 Health at a glance** for any user: a verdict on four axes (memory is found, memory is right, its cost is reasonable, the pipeline flows), each with its reasons and the command that helps.
- **G2 Efficiency, not just uptime**: reach, quality, cost (context, latency, extraction money), bank health, pipeline flow.
- **G3 Drill-down** from any number to the projects, sessions, days and single memories behind it.
- **G4 Parity**: a page shows nothing that `backsight stats <view> --json` does not return; the API returns what the CLI prints (equal on the same data and a frozen clock, the `index` block aside).
- **G5 Developer views**: releases and settings compared on real history, honestly labelled as observational.
- **G6 Structured local data** with a real schema and a migration system that `update apply` runs and a rollback survives.

### Non-goals
- A monitoring stack: no alerting, no paging, no Prometheus scraping.
- Editing memory from the browser: read-only; every action is a CLI command shown for copying.
- Multi-user or remote access: one user, loopback only; other processes of the same OS user are out of scope.
- Replacing `stats`, `why`, `feedback log`, `memory stale`, `projects` or `doctor`: they stay.
- Judging memory text with an LLM: the binary calls no LLM (§2).
- Changing recall behaviour to measure it (hold-out experiments): a separate decision if ever wanted.

### Anti-goals (failure even if it "works")
- The prompt hook slower or less reliable because of this work (hooks never open the metrics index; block 7's ledger read is bounded and falls back).
- Memory text, prompt text, error text or config strings copied into any new file, or shown without an explicit click.
- A number without its sample size; a percentage over a handful of events presented as a fact; a banner that cries wolf, or stays green while the server is down.
- A dashboard number an agent cannot get.
- Opening a page costing tokens, money or a write on the server.
- An update that leaves an install unable to read its metrics, or a rollback that breaks them.
- Goodhart: nothing on the dashboard feeds recall.

## Principles
- **P1 One read model.** All numbers come from `internal/metrics`; the CLI views and the HTTP handlers call the same functions with the same arguments; a page and its API share one cached result. The one exception is memory text (§7), which is not a metric.
- **P2 Read-only and free.** Pages read local files, the local index and the server's GET endpoints. No POST to the server, no LLM call; the only writes are the index's own (ingest), the dashboard's runtime files and its login codes (§7).
- **P3 Ids, numbers and enums.** The index and every new file store ids, numbers, enums and timestamps, never memory text, prompt text, error text or config strings. Text appears only for one memory, fetched live, after a click (or `stats memories <id> --text`).
- **P4 Honest numbers.** Every rate shows numerator and denominator; under its minimum sample it reads "too few"; its status uses the confidence bound, not the point estimate; "not declared" is its own category, never a miss; window metrics use raw journal counts, ledger figures say they are recent-weighted.
- **P5 Every number explains itself and leads to an action** (catalog, §3).
- **P6 Scope is always said.** Activity is this PC's (telemetry and journal are per machine); bank, extraction and server numbers are the server's, shared by every PC on it. Every widget carries a "this PC" or "server" chip.

## Decision

### 1. The local metrics index (block 1)

- **Engine**: SQLite through `modernc.org/sqlite` (pure Go; release builds stay `CGO_ENABLED=0` on the four targets of SPEC §16). Pragmas set per connection in the DSN: `journal_mode=WAL`, `busy_timeout=5000`, `foreign_keys=on`, `synchronous=NORMAL`, `journal_size_limit=67108864`, `_txlock=immediate`. One writer connection per process; ingest is single-flight per process.
- **File**: `<state>/index/metrics.db` (with `-wal`, `-shm`). The directory is created 0700 (on Windows the user profile's default ACL applies, as for the rest of the state directory). `internal/paths` gains `IndexDir()`; `paths` prints it. `uninstall --purge-local` removes the state entries it knows (an allowlist, `internal/cli/uninstall.go`): `index/`, `metrics/`, `dashboard/` and, with block 7, `feedback/ledger.db*` join it, and its kept-data test covers them. `report` never includes them.
- **What it holds**: rows derived from local files; never the source of truth for anything. Sources:

| Source | Ingested as |
|---|---|
| telemetry month files | typed tables for: prompt, outcome, reply, briefing, briefing_outcome, tool, tool_use (raw: `ids` count and `memory_ids` array handled apart), credit, credit_check, retire, feedback_settle, feedback_error, gate, retain, hook_failure, job, attribution, store, dashboard, config; common columns `ts, session, project, binary_version, v`, `n` nullable (only the kinds that carry it). Other and unknown kinds: `events(ts, kind, session, project, binary_version)` with **no payload** unless a field is on a per-kind allowlist in code (default deny); `error` and any free-text field are never on it |
| journal month files | `turns`; `shows` (one row per item: key, ts, session, turn, agent, path, memory_id, rank, reranker, boost, rank_without_boost, score_without_boost, project); `settles` (key, memory_id, show_at, outcome, settle_ts); `credits`; `stops` (turn, agent, outcome, flags, journal order); `retirements` (forget, retire, hide, unhide); `recalls`; `imports` (kept apart, never in window metrics) |
| the ledger, through a `feedback.LedgerReader` interface (today `feedback.Current` over `ledger.json`, lock-free) | `ledger(memory_id, shown, credits, credits_at, misses, misses_at, last_shown, last_credited, wrong, hidden_since, unhidden_at, imported_shown, imported_credits)`, replaced in one transaction per ingest; the learned-ranking value is computed at read time from the config's parameters. Block 7 swaps the reader's implementation, nothing else |
| `state.json`, `reach.json`, `breaker.json`, outbox and quarantine | `local_status`, one row, counts and timestamps only, replaced per ingest |
| block 6 files (§11) | their own tables |

  Session state files are not ingested (they hold memory text). Free-text fields are never stored: errors, reasons and failure details become closed enums (and an HTTP status where there is one); a value outside the enum is stored as `other`. Block 2 switches the existing `feedback_error` emitters from `error: err.Error()` to an enum `reason`.
- **Derived definitions the ingest fixes once**: a turn's **final stop outcome** is the last `stop` row for (session, turn, agent) in journal order; a `blocked` row with no later row counts as `undeclared`. A retained **document's status** is its last `retain` event's status (a document is `queued` by the hook, then `ok` from the tick).
- **Ingest** (`internal/index`): incremental and idempotent. A cursor per source file: `(source_file, size, offset, head_len, head_sha256 of its first head_len ≤ 4096 bytes, ingested_at)`; every row carries its `source_file` so a file's rows can be deleted exactly. Each run reads from the offset in transactions of at most 5,000 lines, advancing the cursor in the same transaction. A file shorter than its offset, or whose first `head_len` bytes changed, is re-ingested from 0 after deleting its rows. A line that does not parse, or a known kind missing a required field, is skipped and counted in `ingest_errors(source_file, offset, reason enum, at)` (30 days kept). A last line without its newline waits for the next run.
- **Vanished files** (telemetry rotation after 13 months, a journal month moved away by hand): their rows are **kept**. The index keeps 25 months; `jobs maintain` prunes older rows. A rebuild can only rebuild what is still on disk: `stats index rebuild --plan` lists the months that would be lost, and the rebuild needs `--yes` when there are some.
- **Who ingests**: `jobs tick`, through a step run on every exit path of the tick (inside its `finish`), before the tick's own `job` event, bounded at 5 s (a longer catch-up resumes next tick), followed by `wal_checkpoint(TRUNCATE)`; every `stats <view>` command; the dashboard on each authenticated request (§7). Catch-up before reading is bounded at 2 s; past that the view answers from what is ingested with `"index": {"lag_seconds": …, "partial": true}`. Hooks and the MCP server never open the index. Read transactions are short (one per view) so checkpoints are not starved.
- **First build** after install or update happens on the first `stats <view>`, dashboard start or `jobs tick`, with progress on stderr for CLI callers. Budget: ≤ 20 s for 13 months of generated data on the author's PC.
- **Corruption and full disk**: on `SQLITE_CORRUPT`, `SQLITE_NOTADB` or a failed `quick_check` at open, the file is moved to `metrics.db.corrupt` (one kept) and rebuilt once, automatically; a second failure in 24 h stops and doctor reports it. A full disk aborts the transaction and leaves the file as it was.
- **Rebuild** (`stats index rebuild [--plan] [--yes]`) builds `metrics.db.tmp`, then renames it over `metrics.db`; when the rename fails (Windows, a dashboard holding the file) it says to close the dashboard and run again, and the old index stays.
  *As built (block 1, see decisions/INDEX.md)*: the temp file is `<file>.tmp-<pid>-<rand>` under `index/rebuild.lock`, not a fixed `metrics.db.tmp`.
- **Network and synced folders**: SQLite's WAL is unsafe there. The `metrics-index` doctor check warns when the state directory is on NFS, CIFS/SMB, 9p (WSL's `/mnt/*`), sshfs or a known sync folder (OneDrive, iCloud Drive, Dropbox); the index then opens with `journal_mode=DELETE`.
- **Commands**: `stats index` (file, size, schema version, per-source lag, ingest errors in the last 30 days, side, aside or corrupt files; `--json`), `stats index rebuild [--plan] [--yes]`.
- **doctor** `metrics-index`: Info when not built yet; Warn when unreadable after the automatic rebuild, with ingest errors in the last 24 h, with a lag over 1 h while `jobs tick` runs, or on a network or synced folder; fix `backsight stats index rebuild`.
- **Dependency gate**: `modernc.org/sqlite` added with `make licenses`; `govulncheck` green. Measured on the four release targets and stated in the PR: stripped binary size delta (gate ≤ +10 MB) and the cold start of `backsight hook user-prompt-submit` on a no-op (gate: p95 delta ≤ 5 ms over 200 runs). Block 1 starts with this measurement; past either gate, the work stops and the author decides.

### 2. Schema migrations, updates and rollbacks (block 1)

- **Migrations**: numbered SQL files embedded in the binary, `internal/index/migrations/NNNN-slug.sql`, forward only, append-only registry (a released migration is never edited, renumbered or removed, as in `internal/migrate`). Each runs in its own transaction and is recorded in `schema_migrations(id, sha256, applied_at, binary_version)`; `PRAGMA user_version` holds the highest applied number. A test pins the SHA-256 of every released migration (each release updates the pinned list); an edited released migration fails it.
- **Applied on open** inside `BEGIN IMMEDIATE`; a process that waited re-reads `user_version` and finds nothing to do. **Except during an update**: while `update apply`'s uncommitted marker exists (the marker it writes before the shim switch and clears at the commit point), opening never migrates; a view that needs a migration then fails with exit 20 ("an update is being applied, try again in a minute") and the dashboard shows that sentence.
- **In `update apply`** *(agent's call)*: the index migration runs **after the commit point**, in the "warnings, never a rollback" steps beside `bank apply` and the docs index (`internal/cli/update_apply.go`), as a child call of the new binary: `backsight stats index migrate` (hidden; applies pending migrations, ingests nothing, 60 s bound). A failure is a warning in the update result and in doctor; the next open retries. `update apply --plan` lists the pending index migrations by asking the new binary (`stats index migrate --plan`, a child call like `update migrate --plan`).
- **Rollback**: `update apply`'s rollback restores `state.json` and `config.toml` as today; since nothing migrates before the commit point, a rollback never meets a migrated index.
- **Newer schema** (an older binary meets an index migrated by a newer one, e.g. after a user installed an older release by hand; `update apply` never downgrades): the older binary never writes or renames that file. A short-lived command uses its own file beside it, `metrics-v<its head>.db`, building it if needed; `stats index` names both. A **running dashboard** re-reads `user_version` on each request and, when it is above its head, stops serving data and shows "backsight was updated: restart `backsight dashboard`". A binary that finds side files of a **lower** head than its own deletes them (with their `-wal` and `-shm`) at its next `jobs maintain`, only after a SQLite exclusive-lock probe succeeds.
- **Tests that bite**: a fixture database for each released schema version (`internal/index/testdata/schema-NNNN.db`, a few rows, made by the release that ships the version); a test migrates each to the head and compares `sqlite_schema` with a fresh build (equal) and checks its rows survived. A test applies a test-only head+1 migration, then opens with the real registry and checks that the side file is built and the newer file untouched. A test runs `update apply` with a failing post-commit index migration and checks the update is kept and the warning reported. A test opens during an uncommitted update and checks nothing migrates.
- **Block 7** uses the same machinery for `feedback/ledger.db` (§12).

### 3. The read model and the metric catalog (block 2)

- **`internal/metrics`** sits above `internal/index`, `internal/feedback` (the learned-ranking formula), `internal/state`, `internal/config` and the `hindsight` client; it imports no HTTP server code and no `cobra`. Each view is `(ctx, Source, Query) → (Result, error)`; `Query` is `{window, project, path, machines, limit, offset, sort, state, id, dev}`; `Source` bundles the index, a clock, config and an optional server client.
- **Server reads**: GET only, through a wrapper of `hindsight.Client` that refuses any other method; 3 s timeout each, run in parallel; cached 60 s per (endpoint, query) in the dashboard process only. When the server does not answer, server sections carry `"server": {"ok": false, "error": <enum>, "last_ok": …}` and their metrics read `no_data`. On a client (`server.mode = "remote"`) the calls go to the joined server; on a server-only host, activity sections read `no_data` with reason `server_only_host`. New client methods: `/stats` widened (links, observations, operations by status, consolidation), `/stats/memories-timeseries`, `/tags`, `/llm-requests/stats?operation=`, `/operations` with `created_at`. Block 2 starts by calling each on the author's server (GET only) and recording the real response shapes in the PR; a metric whose endpoint does not deliver reads `no_data` with reason `server_unsupported`.
- **Project filter**: activity metrics (prompts, turns, shows, declarations, sends) filter on the **session's** project; bank metrics filter on the **memory's** project tag; memory tables show the memory's project. Memories of the transverse pool appear under their own name. A widget a filter does not apply to says "not filtered".
- **Catalog**: one Go table `metrics.Catalog` of `Def{id, label, question, definition, unit, aggregation (raw|recent_weighted), direction (up|down|none), min_n, absolute{watch, bad}, relative (bool), error_class (bool), ci (wilson|wilson_approx|none), scope (machine|server), source, action, command, dev}`. `label` is the plain-language name (§9), `definition` the precise one. `stats defs [<id>] [--json]` prints it, with, for rates, the smallest change detectable at the current n; the UI's ⓘ and "what to do" lines come from it; `docs/dashboard.md` holds a generated table checked by a test. User-visible strings follow CONTRIBUTING's public-text rule (`internal/cli/publictext_test.go`): no decision or block numbers, no spec sections.
- **Time windows**: `--days N` (rolling, ending now; default 7) or `--since T [--until T]`; windows are half-open `[since, until)`; the previous window is `[since − length, since)`. Day buckets use the local time zone, named in the result (`window.tz`); days may be 23 or 25 h long around DST; `--tz UTC` forces UTC. The existing `stats` overview keeps UTC and its output unchanged.
- **Time attribution**: quality metrics attribute each show, turn and declaration to the **show's time** (`settle.at` is the show time). Shows not settled yet at `generated_at` count as `pending` in `extra`, never dropped and never misses.
- **Status engine**, one order for every metric:
  1. `no_data` when the source is absent.
  2. `too_few` when the denominator is under `min_n` (p50 needs n ≥ 20, p95 n ≥ 100).
  3. **Absolute thresholds** (only the metrics listed with them in §4): for rates, compared through the 95 % bound on the good side (for a higher-is-better rate, its upper bound must be below the threshold); for percentiles and counts, the value itself. Gives `ok`, `watch` or `bad`. A rate whose point estimate is past the threshold but whose bound is not is `ok` with `borderline: true`.
  4. **Error-class rules** (metrics marked `error_class`): the counts and ages written in §4's Status column, on the value itself, immediately. Gives `ok`, `watch` or `bad`.
  5. **Relative thresholds** (metrics marked `relative`): `watch` when the good-side bound is more than 30 % worse than the median of the point values of the four previous 7-day windows that have n ≥ `min_n` (if at least two of them do), in the metric's direction: below 0.7 × the median for a higher-is-better metric, above the median / 0.7 for a lower-is-better one; never `bad`.
  6. The status is the worst of 3, 4 and 5.
  - `unreliable` is set on `used.turn_rate` while `declare.coverage`'s upper bound is below 80 % (§4).
  - Intervals: `wilson` where the unit is independent (prompt, turn); `wilson_approx` where units cluster (declarations within a turn), said in the ⓘ; `none` for show-level and per-session ratios and for percentiles.
  - *(2026-11-09, as built in block 9: a metric judged on its p95 whose p95 could not be computed (fewer than 100) reads `too_few`, never `ok`; it changed `pipeline.time_to_recall` only, whose page pill now shows the view's status. A window over 400 calendar days (counted in its zone) or with a date outside 2000-01-01 to 2099-12-31 is refused: CLI exit 2, API 400, the page's bad-request state; 400 covers `--days 365`, the date picker's 397 days and the 13-month calendar, and matches the daily document's cap.)*

### 7. `backsight dashboard` (blocks 4 and 5)

- **Command**: `backsight dashboard [--port N] [--open]` serves on `127.0.0.1` only (no option binds elsewhere). Default port 0 (a free port chosen at start); `--port` for a fixed one, exit 2 if taken (on Windows the socket is bound exclusively). Runs in the foreground; stops on interrupt or after 2 h without a request. *(2026-10-31, as built in block 4, R8: only signed-in requests and logins keep it alive, not any request; a probe or a stray tab must not keep it running.)* Prints `Dashboard: http://127.0.0.1:<port>/?code=<code>` (`--json`: `{url, port, expires_at}`); `--open` opens it in the default browser (`xdg-open`, `open`, `rundll32 url.dll,FileProtocolHandler`). *(2026-10-31, as built in block 4, R31, accepted risk: `--open` puts the one-time link on the opener's command line for a moment, visible to other local processes; the code works once and expires in 2 minutes.)* No config key (an unknown key would break a rolled-back older binary's strict config load). - **Runtime file** `<state>/dashboard/dashboard.json` (0600): `{pid, port, started_at}` only, no secret; removed at exit. - **Login codes** *(agent's call, from the review)*: a code is 128 random bits. Whoever mints one (the dashboard at start, or `backsight dashboard link`, which prints a fresh link for the running dashboard) writes only `sha256(code)` as an empty file `<state>/dashboard/codes/<hex>` (0600) and prints the code. The server accepts a code by deleting that file (exactly once, no clock, no nonce list); a file older than 120 s is refused and removed. Only a navigation consumes a code: GET (not HEAD), `Sec-Purpose`/`Purpose: prefetch` refused. Accepting creates a session: a cookie `backsight_dash_<port>` holding a separate 256-bit secret (`HttpOnly`, `SameSite=Strict`, `Path=/`, no `Expires`), then a redirect to the same host and path without the code. *(2026-10-31, as built in block 4, R30, accepted risk: browsers do not separate cookies by port, so the cookie reaches any other service the same browser opens on `127.0.0.1` (or `localhost`), which could replay it until 2 h without use or the stop; `docs/privacy.md` and `docs/dashboard.md` say so, including the `ssh -L` case.)* Sessions expire after 2 h idle; at most 8 live sessions (the oldest dropped). Secrets compare in constant time. A request without a valid session gets a 401 page saying to run `backsight dashboard link`. Authentication happens before any work: no ingest and no server call for an unauthenticated request. `report` never includes `dashboard/`.

No CORS headers, ever. `http.Server` with `ReadHeaderTimeout` 5 s, `MaxHeaderBytes` 16 KiB, a 10 s render timeout. Every response: `Content-Security-Policy: default-src 'none'; style-src 'self'; img-src 'self' data:; script-src 'self'; connect-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store` (assets excepted), `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-origin`. `/assets/…` (static, no data) is served without a session so the 401 page can show its logo and styles. No CDN, no remote font, no outbound request from the page.

### 12. The ledger in SQLite (block 7)

**Changed from the chat** *(agent's call, from the security review)*: the author approved moving "the journal and the ledger" into SQLite as a source of truth. A database as the only copy of the feedback history can be lost whole (corruption, a full disk mid-write, a sync tool or antivirus) where an append-only file loses at most a line, and rollbacks would need exports. So **the journal stays the append-only JSONL files, the source of truth, for good**, and the **ledger** becomes a SQLite database derived from it:
- **File** `<state>/feedback/ledger.db`; pragmas in the DSN (WAL, or `DELETE` on network and synced folders as in §1; `synchronous=NORMAL`; `busy_timeout` 20 ms in hooks, 5 s elsewhere). Own migration registry (`internal/feedback/ledgerdb/migrations/`) under §2's rules, the update-in-progress and newer-schema rules included. *(2026-11-09, as built in block 7, R22: the writer uses `synchronous=NORMAL` with WAL and `FULL` with `DELETE` on network and synced folders, as the index does; the issue said NORMAL. - **Tables**: `memories` with every field of today's entry (shown, credits, `credits_at`, misses, `misses_at`, last shown, last credited, wrong, hidden since, verdict and note, `unhidden_at`, imported shown and credits); `meta` (params, `history_imported`, schema); `ledger_cursors(file, offset)`, one per journal month file; `settled_keys(key)` unique. *(2026-11-09, as built in block 7, R6, amended during implementation: the imports choice is `meta.imports_dropped_before_ns`, the time of the last `--no-import` rebuild. ### 13. Several PCs (block 8)

- **Publishing.** With `feedback.enabled` and `feedback.share_ledger` both on (one is not enough: R5), `jobs tick` publishes a daily aggregate document `backsight:metrics:<machine_id>` to the control bank, once per UTC day (R4: the same mechanism and guards as the shared counts, `retain.WriteControlDocument` and the `shareTarget` guard, but its own daily resend rule, sent even when the figures did not change, after a 0-59 min offset from 00:00 UTC that spreads the PCs, a failure retried after 1 h). It waits for a full index catch-up and is retried at the next tick otherwise (R43). A server-only host publishes nothing and only reads (R36). The document is JSON `v` 1 with compact `[numerator, denominator]` pairs (R2), covers complete UTC days only, at most 400 and ending the day before the publish (R3), and holds: per day, the flagship figures (prompts, prompts that got memory, used and declared turns, wrong verdicts, context characters and sessions, documents sent), latency counts in fixed buckets (8 edges from 50 ms to 5 s, one open bucket above: R6), and per-version figures for the Releases metrics, at most 8 versions a day (R12, R45); and, once, the binary version, the OS as a closed enum (linux, darwin, windows, other: R28), the machine id and the first-seen date, which is that of the first successful publish (R27). **No memory ids, no project names, no session ids, no text, no hostname.** A PC is labelled by the first 8 characters of its `machine_id` (13 when two counted PCs collide: R47), its OS and first-seen date (no config key: an older binary's strict config would reject one). A writer drops the version breakdown of the oldest days first, then the oldest days, to stay within 256 KiB (R13); a reader refuses, never trims, a document over 1 MiB or 400 days.
- **Reading.** `jobs tick` fetches the other PCs' documents every 6 hours from the listing the shared counts already take (R15, R44), parses each strictly as untrusted data, and caches the canonical form in `<state>/metrics/machines.json`, at most 64 PCs; the index ingests it (migration 0003) and views read only the index. A document that is too large, written by a newer backsight (`v` 2) or not valid is ignored and counted. A PC counts while its last send is within 30 days and not more than 24 h ahead (R17); after 48 h it is stale, still counted, with its days "up to <date>".
- **Merging.** Every view gains `--machines this|all` (default `this`, the API's `machines=`: R30, R42); `all` labels the scope "all PCs on this server (N)", N counting this PC (when it shares and is not a server-only host) and every counted PC, stale and idle ones included (R18). Rates sum numerators and denominators and go through the unchanged status engine (R8); context is total characters over sessions (R7); latency comes from the merged buckets, nearest rank, and reads as a range with "approximate", its status word exact (R6, R33); another PC's day counts in a window when its 12:00 UTC is in it (R10). Views that merge: overview, quality, cost, pipeline, days and releases; bank and system have nothing to merge, and projects, sessions and memories always answer this PC's (R20). This PC's part is always live from its own index (R11); the verdict, the attention list, Lately and every list stay this PC's, and `pipeline.flow` merges its value but keeps this PC's status (R9). Project filters do not apply to other PCs' figures, which are added whole and tagged. With sharing off, `all` answers this PC's figures and `scope.pcs.sharing` says why (R19). Every view carries `scope.pcs`, and `view_schema` stays 1 (R21).
- **Machines.** System gains a Machines card: each PC's label, OS, first seen, last sent, backsight version and whether it counts, ignored documents with only a valid short id and the reason (R22, R39); the doctor check `machines-share` warns when publishing has failed for more than 24 h (R41). `uninstall --purge-local` deletes the PC's document beside the shared counts (R29).
- **Memory.** Memory pages show the other PCs' recent-weighted used and ignored counts from `shared-combined`, beside this PC's, in both modes (R23).

## Options rejected
- **Postgres** (the server's or another): clients reach the server through its API only, hooks must work while the server is down, and backsight never takes over Hindsight's database (0036).
- **DuckDB**: needs cgo (release builds are CGO-free) and allows one writing process at a time.
- **The journal itself in SQLite** (approved in chat, then changed, §12).
- **Reading JSONL on every page**: fine at 2 MB, not at 400 k events a year, and joins become ad hoc code.
- **A separate `metrics` command**: two overlapping entry points; one noun with views is easier to learn.
- **A JavaScript single-page app**: an npm toolchain and supply chain in a Go repository, and a page that needs scripts.
- **A show-level "used" rate as the flagship**: ranking decides which shows count, shows cluster in turns, and showing fewer, safer memories inflates it.
- **Cost per used memory as a flagship**: today's extraction cost over credits for memories extracted weeks earlier, unstable and unbounded at low counts; replaced by `memory.yield`.
- **A long-lived token in the URL**, or an HMAC minting key in a file: the first leaks through the process list, browser history and transcripts; the second is a reusable secret on disk. One-time codes claimed by deleting their hash file instead.
- **A verdict that follows the selected window**: the banner would flip with the selector.
- **LLM-judged audits** and **hold-out experiments**: the binary calls no LLM; suppressing recall changes the product.
- **A LAN bind**: memory ids and project names on the network for little gain; `ssh -L` covers remote viewing.
