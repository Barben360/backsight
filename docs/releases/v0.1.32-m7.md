**Pre-release.** Linux amd64 is tested; Windows amd64 is tested in CI, with no new run on a Windows PC for this release. The Linux arm64 and macOS binaries are built but not tested.

Update from any earlier v0.1 with `backsight update apply`: it takes a verified backup first and rolls back if a step fails. Then restart Claude Code, so it reads the memory tools' new texts and the new plugin, and a running dashboard (Ctrl+C, then `backsight dashboard`). New install: see below.
- The server is unchanged (Hindsight 1.2.0): no server upgrade.
- The instruction set is v16 (v13 before): one short guide, shorter memory tool descriptions, and the store rules below.
- The memory bank gets a new template, with the new extraction rules below: it is sent once, at the next bank apply, which `update apply` runs. Memories already extracted are not extracted again. On a PC that uses another PC's server, the server's PC sends it once that PC is updated.
- The plugin is generated again by the new binary's `client install`, which `update apply` runs: the `PostToolUseFailure` hook is now wired only while `recall.failure_pitfalls` is on (off by default). Restart Claude Code to load it.
- The metrics index's schema changes: it gains a table for the end-of-turn check's outcomes and three columns for searches, and keeps every table it had. `backsight update apply` migrates it once the update is committed, and an older backsight that opens it afterwards works on a side file of its own ([A newer index](../troubleshooting.md#the-metrics-index)).

Once, on its first runs after the update, the new version does these things on the server, with nothing for you to do:
- **The first `jobs tick`** gives every briefing page (`backsight-brief-*`) the 6-hour refresh floor and the current briefing request, in one update per page. That update may make the server rewrite the page once, from the new request: about 130,000 input tokens per page (about 1 cent with a Claude Haiku model). A page the server refuses is tried again at most hourly, and `jobs maintain` checks the pages again every day, and again after a restore or a change of bank.
- **The first `jobs maintain`** sets the briefing pages before its subagent sweep and before an automatic update. Then, once its daily backup has succeeded (that backup still holds them), it deletes the stored subagent reports that fail the new report rule (below): their documents, their facts and the observations drawn from them, as `forget --purge` does but without tombstones, so a subagent resumed later reports again under the same document. The purge makes the server consolidate those observations again from their other sources, once, with its own LLM provider. It runs once per value of `hooks.subagent_report_min_chars`: again only when you change it or restore the server. It waits for the next day when that backup failed, when the server does not answer, or while a backup, a restore or a purge holds the maintenance lock. On several PCs, any of them may run it: a second run finds nothing left. This is the only memory backsight deletes without a command from you.
- **The notes queue**: a short subagent report queued by the earlier version and not sent yet is dropped when the queue is sent, under the same rule.
- **Metric definitions**: `used.turn_rate` and `declare.coverage` no longer count the briefing or the similar memory of a `memory_store` answer as memories shown, so they can move once from the update on.

## What changed

**A third of the cost, the same memory.** An audit of one well-used install (three weeks of sessions, a week of the server's LLM log) found most of the server model's work redone for nothing: the end of long sessions extracted again at every small append, briefing pages rewritten after every consolidation, and one-line subagent status reports extracted one by one. On that install, the server's model cost about 57 USD a month at Claude Haiku prices; with these changes it is expected at about 15 to 20 USD a month (`backsight stats cost` shows yours). On Claude's side, the memory text Claude reads again on every call of a session (the guide, the memory tools' instructions and descriptions) is 38% shorter, about 4,600 characters instead of 7,400, and a `memory_store` answer is about 185 characters instead of 2,200. Replays of that install's sessions checked the memories stay as good: see each change.

- **Long sessions are appended less often** (https://github.com/Barben360/backsight/pull/232). Each append to a session already on the server makes it cut the session again and extract the changed end again, so small appends recreated the same memories over and over (63% of the facts consolidated replaced one that existed). `jobs tick` now appends a session's new turns once 30,000 characters wait (`retain.append_min_chars`, the size of the pieces the server cuts a session into), or once the session's last send is 6 hours old (`retain.append_max_wait`). A session's first send, the send when it ends, `backsight retain flush` and a backfill never wait; when the send at a session's end fails or never runs, its last turns go at the latest 6 hours after its last send. On that install's sessions: 75% fewer appends. **What you may notice**: what a long session still open learns reaches your other sessions up to 6 hours later, unless it ends sooner. `backsight retain waiting` names a session held this way (`append_gate`, "waiting for 30,000 characters or 6 h").
- **Briefing pages rewritten at most every 6 hours** (https://github.com/Barben360/backsight/pull/234). The server rewrote every stale page after each consolidation: about 50 rewrites a day for 4 pages read about 5 times a day, 31% of the server's LLM cost. Pages now get a refresh floor, `recall.briefing_refresh_interval` (`"6h"`): new pages at creation, older ones at the first `jobs tick` after the update, and `jobs maintain` sets it again every day. A briefing can be up to 6 hours behind the newest memories; `memory_search` finds them. Each PC sets its own value on every page: keep the same on every PC sharing a server. Setting it replaces the page's whole refresh trigger, so a trigger field changed by hand on the server is reset. Doctor's `bank` check warns about a page with another trigger, and names its fix (`backsight jobs maintain`).
- **Short subagent reports are no longer stored** (https://github.com/Barben360/backsight/pull/235). A subagent's final report under 400 characters with no URL, no issue or pull request reference (`#123`, `owner/repo#123`, `PR 205`, `GH-7`) and no commit hash is not sent any more (`hooks.subagent_report_min_chars`). On that install, 1,274 of 1,406 reports were under 150 characters ("Reading x.go", "Waiting for CI"); each cost an extraction, and the memories drawn only from them were used once in 112 shows. A short report already queued by an older backsight is dropped when the queue is sent. The reports stored before are deleted once (above). An older backsight on another PC keeps sending short reports until it is updated; they are swept at the next change of the setting or the next restore.
- **`memory_store` answers are shorter** (https://github.com/Barben360/backsight/pull/233). They listed the 3 most similar memories in full, which matched the new fact in 1.4% of stores and made up 40% of the memory text in Claude's context. The answer now shows at most one, only when it scores at least `recall.store_similar_min_score` (0.8), on one line cut at 200 characters; otherwise the saved line alone. `🧠🔄 Updated` names the memory it replaces. The memory shown counts as shown in the session: `memory_credit` accepts it with any verdict, where 16 of 139 credits were refused because an id came only from a store answer.
- **After a compaction, the briefing only when it changed** (https://github.com/Barben360/backsight/pull/231). The guide comes back as before. The briefing page, and the last memories shown, come back only when the server rewrote the page since the session got it (with its age right); otherwise one line, `Memory briefing unchanged since this session started: memory_search finds what the summary lost.` One session got the same page 10 times unchanged. The ids of the notes stored in the session come back either way, now as short ids.
- **The steps of the work stay out of memory** (https://github.com/Barben360/backsight/pull/237). The bank's extraction rules keep one fact per delivered outcome (a pull request merged with what it closes, a release published, a setting changed and where) and no longer extract the steps: commits, pushes, branches, rebases, CI runs and their status, pull requests opened or updated, waiting. Claude is told not to store merges, releases or CI status, which the conversation already records, and to close the loop when a recalled open item is settled. Replayed on 14 sessions: 64% fewer process-step facts, 95.5% of the durable facts kept and 97% of the delivered outcomes. Memories extracted before are not changed.
- **One guide, shorter tool descriptions** (https://github.com/Barben360/backsight/pull/238). Each rule is said once, where Claude always has it: the guide given at session start keeps the conversation's rules (read the issue or link the prompt points at first, answer in your language, never ask for a key in the conversation) and goes from about 1,200 characters to 230; the memory tools' instructions hold the credit ask and what to store; each tool's description says when and how to use it (`memory_store` 40% shorter, `memory_credit` 42%). The briefing request now asks for the project's standing process rules (how it releases, how pull requests are opened and merged, worktree and branch conventions), which 13% of searches looked up again every session; pages are rewritten from it at their next refresh.
- **`PostToolUseFailure` wired only when it is on** (https://github.com/Barben360/backsight/pull/236). With `recall.failure_pitfalls` off (the default), a failed tool call starts no backsight process. After changing that key, run `backsight client install`; until then, `backsight doctor` and the session's first line report the plugin's wiring as drifted.
- **Figures to check the savings** (https://github.com/Barben360/backsight/pull/239):
  - **The briefing page counts as shown**: its first line is tagged `[<project> · page]`, and Claude can credit it with `memory_credit` (`page` names it), never report it wrong or outdated, since it summarises memories and is not one. It is never a miss, a page alone never holds a turn at its end, and no figure on memories counts it.
  - `search.empty_rate` gains the queries asked, the queries none of whose hits were returned, and the characters a search answer adds to Claude's context. A new developer figure, `stopcheck.block_yield`, says how often a turn held at its end then credited a memory, with its card on Quality (`--dev`).
  - Subagent reports and backfilled stores carry their session id, like other notes.
  - **Memory figures leave the briefing page and store answers out** (https://github.com/Barben360/backsight/pull/242): the briefing page's id and the similar memory a `memory_store` answer shows are not counted in memory yield, the recall funnel, Helped most or the never-used list.
  - **Docs**: [troubleshooting](../troubleshooting.md#seeing-what-the-servers-model-was-asked) explains how to see, for a day, what the server's model was asked, and what that exposes.
- **New settings**, with their defaults; backsight writes none of them in `config.toml`, so the defaults apply ([configuration](../configuration.md#recall-what-reaches-claudes-context)):
  - `retain.append_min_chars = 30000` and `retain.append_max_wait = "6h"` (`0` and `"0"` turn the wait off);
  - `recall.briefing_refresh_interval = "6h"` (`"0"`: no floor);
  - `hooks.subagent_report_min_chars = 400` (`0` sends every report);
  - `recall.store_similar_min_score = 0.8`.

  An older backsight refuses a `config.toml` with a key it does not know: remove the ones you set before installing an older version (a failed `update apply` puts back your `config.toml` itself).

## Install

On Linux:

```sh
curl -fsSL https://raw.githubusercontent.com/Barben360/backsight/main/scripts/install.sh | sh
backsight setup
```

On Windows x86_64, in PowerShell:

```powershell
powershell -ExecutionPolicy ByPass -c "irm https://raw.githubusercontent.com/Barben360/backsight/main/scripts/install.ps1 | iex"
backsight setup
```

Requirements as for v0.1.22-m7. On Windows, Claude Code must find Git Bash: if Git for Windows is portable or installed in a place of your own, set `CLAUDE_CODE_GIT_BASH_PATH` to its `bin\bash.exe` (doctor's `git-bash` check gives the command).

## Known limits

- Dashboard:
  - Version switches and settings changes are marked on a day's page and on Releases only, not on every chart.
  - The custom window goes back 13 months, as far as this PC keeps its history.
  - Time to recall needs a few days of history, and 20 sessions before it shows times.
  - Memory yield needs four weeks: a week counts 28 days after it ends.
  - On a window over 200 days, charts show no per-day values on hover, and "Show as a table" lists the latest 120 days.
  - A week that is not complete shows no count of new memories.
  - The project filter takes a typed name, not a pick from a list (the Projects page lists the names). The Projects list cannot be sorted. The context card names the session budget rather than showing its value.
- GPU reranker:
  - It needs the Docker runtime, on the server's PC.
  - Tested on one NVIDIA RTX A2000 (Linux) and one AMD Radeon 890M (Linux). Intel GPUs, macOS and Windows are not tested.
- Owner checks:
  - The short-lived native units created during install, start and restore are not checked.
  - On Windows, when neither `schtasks` nor the task's file can be read, the task is driven as before.
- `retain resend-failed`: it does not cover notes and sub-agent reports sent while extraction failed (the queue drops them once sent). A transcript rewritten or moved after its worktree was deleted loses the project recorded for those turns, so the session is then filed by today's rules.
- The metrics index: an index already in write-ahead mode whose folder no longer allows it fails its writes until the state directory is back on a local disk. `stats days` reads a year of prompts with no index for it (about 0.1 s locally).
- Import: a file the server keeps rejecting holds that folder's next files until it passes. The last tick before a cap can overshoot it by what was already in flight. A file deleted from the folder stays in the memory until `import purge`.
- Windows:
  - WSL is not tested, and Windows on Arm has no binary.
  - The native runtime is the only runtime there (`server runtime switch` is refused). It serves this PC only, has no web UI, and starts with your logon, not at boot.
  - `backsight server status` keeps showing the server's last refusal while it is stopped, until a start passes the check.
  - backsight's `.exe` files are not code-signed: SmartScreen or Smart App Control may warn about them. The install script checks the release signature before it runs anything.
- A new install reads "learning" for its first week, and some numbers read "too few" until enough prompts and turns accumulate.
- Extraction cost needs a price: the built-in table's, or one set under `[llm]` in the config file for another model (doctor's `price` check says when none is known). The server reports token counts for all PCs together.
- On native, PostgreSQL is 18.1 with pgvector 0.8.5, where the Docker image runs 18.6 with 0.8.7; `backup verify` runs in the runtime that will restore.
- Claude cannot run `/reload-plugins`: after an update from the session, you type it.
- A LAN address carries the API key in clear; a tailnet address encrypts it.
- The shared part of a session continued on two PCs may be stored twice.
- Several PCs: a PC sends its figures once a UTC day, up to the day before, so another PC's today is not in all PCs until the next day; the others' figures are fetched every 6 hours. A PC counts in a window by the noon (UTC) of each of its days. The other PCs send no project, session or memory: Projects, Sessions and Memories stay this PC's, and a project filter does not narrow the others (`other PCs: not filtered`). The verdict stays this PC's. Speed across PCs is a range from time buckets, never an exact time, and the PCs' figures are trusted as sent: nothing signs them.
- Several PCs on older versions: until it is updated, another PC appends its long sessions every 15 minutes, sends short subagent reports, and makes briefing pages without the refresh floor (this PC's next `jobs maintain` gives them the floor). The savings above are those of one install, worked out from its logs; yours show in `backsight stats cost` after a week or two.
